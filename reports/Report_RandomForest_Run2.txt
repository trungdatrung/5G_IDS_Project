PART 2. PARAMETER SEARCH RESULTS (STEP 2) AND THRESHOLD SELECTION (STEP 3)
================================================================================
Search space (following Probst et al., 2019):
  max_features     : 'sqrt', 0.1, 0.2, 0.3, 0.5
  min_samples_leaf : 1, 2, 3, 5, 10
  max_samples      : None, 0.5, 0.7
  class_weight     : None, 'balanced', 'balanced_subsample'
  max_depth        : None, 20, 30

Best parameters found (CV PR-AUC = 0.9829):
  max_features = 0.5    (run 1: 'sqrt', about 0.074)
  max_samples  = 0.7    (run 1: None, i.e. 100%)
  max_depth    = 20     (run 1: unlimited)
  min_samples_leaf = 1, class_weight = None (same as run 1)

Observations:
  - The top 10 combinations differ by only 0.0007 PR-AUC (0.9822-0.9829),
    smaller than the standard deviation across folds (about 0.0015). The
    parameter "surface" is very flat: picking any combination from the top
    group gives roughly equivalent results. This matches Probst et al.'s
    finding that Random Forest is fairly robust to its default parameters.
  - class_weight doesn't help, since the train set is already nearly
    balanced (50/50).

Decision threshold:
  - Selected via CV on 80% of train: 0.505
  - Selected via CV on 100% of train (final model): 0.515
  -> The optimal threshold is nearly equal to 0.5. Reason: CV is performed on
     data with the same distribution as train (50/50, the model's
     probabilities are fairly well-calibrated), so the default threshold was
     already close to optimal. Selecting the threshold "cleanly" (without
     using the test set) barely changes the result.

Observations:
  - Both methods confirm the "TCP handshake timing + reply traffic" group as
    the core (ackdat, dload, dbytes, synack, tcprtt).
  - MDI overrates dload (0.245). Permutation shows sbytes, smean, and
    service matter more than MDI suggests. This matches the warnings from
    Strobl et al. (2007) and the scikit-learn docs: MDI is biased toward
    continuous and correlated features.
  - tcprtt drops from rank 3 (MDI) to rank 8 (permutation), because
    tcprtt = synack + ackdat. When tcprtt is shuffled, the model can still
    recover the information from ackdat/synack.
  - Note: run 2's model uses max_features=0.5, so MDI attribution differs
    from run 1 (dload rises to rank 1). The MDI tables between the two runs
    should not be directly compared.

PART 6. SUPPLEMENTARY EXPERIMENTS ON DISTRIBUTION SHIFT (STEP 5) - REFERENCE ONLY
================================================================================
These experiments use only the test set's FEATURES (not labels) to measure
the shift, and look at the result directly on test. They are not used to
select the main model.

Train/test shift (adversarial AUC): 0.8040, matching the earlier diagnostic
run (0.8020).

                                    Acc     Prec    Recall  F1      FPR     PR-AUC
  Run 1 (baseline)                 0.8176  0.6807  0.9459  0.7917  25.67%  0.9287
  Run 2 - main (step 4)            0.8276  0.6951  0.9436  0.8005  23.95%  0.9428
  5a: threshold chosen on a
      "test-like" validation
      (threshold 0.461)            0.7928  0.6454  0.9648  0.7734  30.67%  0.9376
  5b: 5a + importance weighting
      (threshold 0.428)            0.7916  0.6441  0.9644  0.7723  30.84%  0.9369
  5c: step 4 + 4 ratio features
      (threshold 0.485)            0.8221  0.6852  0.9519  0.7968  25.30%  0.9441

Results:
  - 5a and 5b are both WORSE than run 2: Recall rises to 96.5% but FPR rises
    to about 31%.
  - 5c has the highest PR-AUC and ROC-AUC (0.9613), the fewest misses
    (FN = 892, 154 fewer than run 2), but a higher FPR, so F1 is slightly
    lower than run 2's.

Explanation: why distribution-shift techniques don't help here
  - The train rows "most similar to test" are 56% Attack (Normal is only
    44%). The region of feature space where test's Normal traffic falls
    (slow handshake, low rate, few reply bytes) is mostly occupied by
    attacks in the train set.
  - Importance weighting only works when the shift is "pure covariate
    shift": the feature distribution changes but the feature -> label
    relationship stays the same, and the train set has enough examples in
    that region. Here, the train set has almost no examples of "slow
    Normal." Upweighting that region effectively upweights Attack samples,
    making the model lean further toward predicting Attack (FPR rises).
  - Selecting the threshold on a "test-like" validation set is biased for
    the same reason, so the threshold drops to 0.46 and FPR rises.
  => This is not something that can be "fixed" with an algorithm on the same
     train data. The model needs more diverse Normal traffic EXAMPLES
     (see Part 7).
  - The ratio features (5c) help the model rank better (higher AUC), a
    promising direction if combined with better data.

  - Overlap between train and test: 1,993 test rows (3.94%) exactly match

    340 Normal. These rows make the test result slightly optimistic,
    equally for both runs. We keep them as-is since this is the dataset

  - The validation -> test gap is still about 10 points (0.9324 -> 0.8276).
    FPR rises from 9.05% (validation) to 23.95% (test). This is the current
    model's main limitation.
  - Each configuration was run with only one random_state (42). Differences
    under about 0.3 points (e.g. Recall by attack type) may fall within

  - Table 4.4 in notebook 03 displayed an extra "Normal" row (n = 0, NaN)

================================================================================
PART 8. CONCLUSION AND SUGGESTIONS FOR RUN 3
================================================================================
Conclusion
  + The evaluation procedure is now correct: validation/OOB exist, every
    choice is based on train data, test is used only once for the main
    model.
  + Overfitting decreased (gap 7.3 -> 4.5 points). Run 2's model is
    slightly but consistently better than run 1: F1 +0.9, Precision +1.4,
    PR-AUC +1.4 points, 551 fewer false alarms.
  - Parameter tuning and threshold selection have nearly exhausted their
    room for improvement on the current data. The remaining bottleneck is
    the distribution shift of Normal traffic between train and test, and it
    cannot be fixed with weighting or thresholds.

Suggestions for run 3 (in priority order)
  1. Add more diverse Normal data. The data/raw folder already has the 4
     full UNSW-NB15_1..4.csv files (about 2.5 million records), from which
     the official train/test set was extracted. More Normal traffic could be
     drawn from these files for training, provided:
       - every record matching the test set is removed (to avoid data
         leakage),
       - notebook 01's exact cleaning pipeline is applied (same features,
         same leaky columns dropped).
     Note that the full files have a different schema (column names, plus
     extra IP/port columns that are metadata and must be dropped).
  2. Try boosting models: HistGradientBoostingClassifier (built into
     scikit-learn), XGBoost, LightGBM, together with 5c's ratio features.
     Use the same validation procedure for a fair comparison.
  3. Select the threshold by operating cost, not just F1. For example, agree
     with the team on "1 missed attack = k false alarms," then use
     TunedThresholdClassifierCV with that cost function.
  4. Analyze Fuzzers separately (Recall about 81%) and the falsely flagged
     Normal flows (state FIN/INT, service http/ftp) to find additional
     discriminative features.
  5. Report results across multiple random_state values (e.g. 5 seeds) to
     get a confidence interval.

References: see Part 5 of reports/Analysis_Overfit_and_Improvement_Direction.txt
(Probst et al. 2019; Bergstra & Bengio 2012; scikit-learn
TunedThresholdClassifierCV; Strobl et al. 2007; Quinonero-Candela et al. 2009;
Arp et al. 2022; ...).
