  => ackdat is the MOST SHIFTED feature in the entire feature set, AND
     simultaneously the model's MOST IMPORTANT feature (perm 0.0501). Its
     median changes 144-fold (0.0002 -> 0.0288). tcprtt changes 59-fold.
     The review's hypotheses 1, 5, and 7 are confirmed with numbers.

  The shift is much stronger when looking only at Normal traffic
  (KS 0.2698 vs 0.0984) - i.e., the shift is concentrated mostly on the
  Normal class, exactly as the earlier report stated.

Categorical variables (total variation distance): service 0.0720 | proto
0.0220 | state 0.0152 (2 of state's levels only exist in test). Much smaller
shift than the numeric feature group.

Class ratio: train-fit 0.4964 / validation 0.4964 / test-dev 0.3665 /
test-final 0.3665.

Adversarial validation (distinguishing train rows from test rows using only
features; 0.50 means indistinguishable):
    Overall AUC    0.8012
    Normal only AUC 0.8722   <- the strongest shift
    Attack only AUC 0.6689

The rule "slow TCP handshake => Attack" (tcprtt > 0.01 s):
                     % Normal slow  % Attack slow  P(Attack|slow)  Attack:Normal
      train              0.1899        0.7748         0.8009           4.02
      test               0.4128        0.7492         0.5122           1.05

  => P(Attack | slow) changes from 0.80 down to 0.51. This is CONCEPT SHIFT
     (the label-feature relationship changes), not pure covariate shift -
     which explains why importance weighting in notebook 03's steps 5a/5b
     failed.

CONCLUSION: the distribution shift is REAL, measured four independent ways,
and concentrated exactly on the feature group the model relies on most.
However, to be precise: these experiments PROVE THE EXISTENCE of the
distribution shift and its overlap with the important feature group - they
do NOT prove a causal relationship with the specific performance level on
test.

6. FUZZERS (Experiment 6)
================================================================================
Claim confirmed. False Negative breakdown on test-final (RF-A):

  Threshold 0.50 - total FN = 472     Threshold 0.711 - total FN = 1,364
    Fuzzers         391  (82.8%)       Fuzzers        1,039  (76.2%)
    Exploits         49  (10.4%)       Exploits         187  (13.7%)
    DoS              10  ( 2.1%)       DoS               45  ( 3.3%)
    Shellcode         9  ( 1.9%)       Shellcode         42  ( 3.1%)
    remainder        13  ( 2.8%)       remainder         51  ( 3.7%)

  Recall Fuzzers: 0.8237 @0.50 -> 0.5316 @0.711. When the threshold is raised
  to cut false alarms, Fuzzers is the category that suffers the most.

MECHANISM - the model does NOT misjudge Fuzzers, it is UNDECIDED about it:

  P(Attack) percentile   Normal   Fuzzers   Attack minus Fuzzers
    q10                 0.0000   0.4173         0.8548
    q50                 0.0000   0.7378         0.9958
    q90                 0.7042   0.9933         1.0000
    mean                0.2331   0.7199         0.9546
    % with P < 0.5      74.3%    17.6%           1.2%

  Fuzzers sits BETWEEN the two groups on the probability scale. Its median
  is 0.74 - above 0.5 but below 0.711. That's why it survives at low
  thresholds and gets wiped out in bulk at high thresholds.

CORRECTING A MISCONCEPTION: the earlier report explained that "Fuzzers'
network flow most resembles normal traffic." Measured directly, this is NOT
quite right - Fuzzers' mean KS versus Normal is 0.2191, HIGHER than other
attack types (0.1766). This means, feature by feature, Fuzzers is not closer
to Normal.

What actually happens: Fuzzers LACKS exactly the features that help separate
other attacks from Normal. The largest gaps in separability are in:
    ct_src_ltm (0.266 vs. 0.181) | trans_depth (0.120 vs. 0.074)
    ct_flw_http_mthd (0.120 vs. 0.074) | sbytes (0.196 vs. 0.164)
And the service composition: 88.6% of Fuzzers falls under service = '-'
(unidentified), versus 71.7% for Normal and 50.8% for other attacks; only
6.3% of Fuzzers goes through http versus 28.3% for other attacks. The
http/connection-count feature group is almost unusable for Fuzzers, so the
model has to rely on a weaker signal.

7. MULTICLASS (Experiment 3)
================================================================================
RF multiclass on attack_cat (attack_cat is NEVER used as an input feature),
with the binary score derived as P(Attack) = 1 - P(Normal).

Multiclass quality on test-final: accuracy 0.7628 | macro F1 0.5242 |
weighted F1 0.7818. By class (precision / recall / F1):
    Normal         0.9455 / 0.8118 / 0.8736     Exploits   0.7356 / 0.8495 / 0.7885
    Reconnaissance 0.8214 / 0.7604 / 0.7897     Generic    0.9601 / 0.6056 / 0.7427
    Shellcode      0.4638 / 0.5189 / 0.4898     Worms      0.7273 / 0.3636 / 0.4848
    Fuzzers        0.3255 / 0.6298 / 0.4292     DoS        0.5452 / 0.2086 / 0.3017
    Backdoor       0.1161 / 0.3476 / 0.1740     Analysis   0.1354 / 0.2207 / 0.1679

  The multiclass problem is HARD on its own: 547 real Fuzzers get called
  Normal, and conversely 2,545 real Normal get called Fuzzers. The two
  classes bleed into each other in both directions.

But for the BINARY task, there is a small, consistent improvement:
    PR-AUC test-dev   : 0.9453 vs 0.9429  (+0.00245, CI [+0.0014; +0.0035])
    PR-AUC test-final : 0.9427 vs 0.9414  (+0.00132, CI [+0.0001; +0.0025], p=0.046)

  Robustness check across seeds (same split, only the forest's random_state
  changes):
    seed 42   : +0.00241      seed 7 : +0.00213      seed 2024 : +0.00232
    Multiclass wins 3/3 seeds. The binary model's own noise spread across
    seeds is only 0.00024 - about 10 times smaller than the effect. So this
    is a REAL improvement, though SMALL.

On Fuzzers - a two-sided result, must be stated clearly:
    At threshold 0.50           : Recall Fuzzers 0.7998 (multiclass) vs 0.8237 (binary) -> WORSE
    At the FPR<=10% operating point: Recall Fuzzers 0.5676 (multiclass) vs 0.5496 (binary) -> BETTER
  Multiclass does not "solve" Fuzzers. It only ranks slightly better in the
  high-probability region, which is where the real operating point sits.

DIFFERS FROM THE REVIEW: the earlier plan expected multiclass to give
+0.005 to +0.02 PR-AUC. In reality it's only +0.0013 on test-final, about
4 times below the lower bound of that expectation.

8. BOOSTING (Experiment 4)
================================================================================
HistGradientBoosting, same features / split / preprocessing / labels /
protocol. Early stopping halts at round 288 of 500. Fit time: 7 seconds
(versus 51 seconds for Random Forest with 300 trees).

    PR-AUC test-dev   : 0.9433 vs 0.9429  (+0.00039, CI [-0.0010; +0.0018], p=0.594)
    PR-AUC test-final : 0.9417 vs 0.9414  (+0.00027, CI [-0.0012; +0.0016], p=0.688)

CONCLUSION: NO improvement. Random Forest is NOT the bottleneck of this
problem. Two algorithm families with entirely different mechanisms arrive at
the same performance level - strong evidence that the current ceiling lies
in the DATA/FEATURES, not the algorithm.

DIFFERS FROM THE REVIEW: the earlier plan expected boosting to give +0.005
to +0.015 PR-AUC. Not reproduced; the real figure is +0.0003 and not
statistically significant.

Scope note: only ONE reasonable configuration was tried, no wide
hyperparameter search (as required). This doesn't rule out a thoroughly
tuned boosting configuration doing slightly better, but a gap this close to
zero suggests that's unlikely.

================================================================================
10. CONCLUSION
================================================================================

GENUINE MODEL IMPROVEMENT (statistically tested)
  - Run 1 -> run 2: +0.0156 PR-AUC, CI [+0.0135; +0.0179]. A real, already-
    known improvement.
  - Multiclass by attack_cat: +0.0013 PR-AUC on test-final (CI [+0.0001;
    +0.0025]), +0.0023 on test-dev, wins 3/3 seeds. This is a REAL but VERY
    SMALL improvement - borderline significant on test-final, and only
    solid thanks to test-dev plus the seed check. Should not be presented as
    a major step forward.

JUST A SHIFT IN OPERATING POINT, NOT A MODEL IMPROVEMENT
  - Run 2 -> run 3: at the same threshold, the two models are
    indistinguishable on any metric (p from 0.27 to 0.86). The entire
    Accuracy/Precision gain comes from the threshold.
  - Every Accuracy gain in this report that comes from moving a threshold
    must be read this way.

NOT STATISTICALLY SIGNIFICANT
  - HistGradientBoosting vs. Random Forest: +0.0003, CI contains 0. The
    algorithm is not the bottleneck.

UNRESOLVED ISSUES
  - Distribution shift: CV 0.9830 vs. test 0.9414. No experiment in this
    round narrows that gap.
  - Fuzzers: still accounts for 76-83% of False Negatives in every
    configuration tried. Multiclass only raises Recall Fuzzers from 0.5496
    to 0.5676 at the operating point.
  - The 8 leaky features are worth +0.011 PR-AUC but are not used. This cost
    is smaller than the ~0.1 AUROC figure the review cited.

WHAT CANNOT BE CONCLUDED FROM THIS ROUND
  - Cannot conclude that distribution shift IS THE CAUSE of the specific
    performance level on test. The measurements only show that the
    distribution shift exists and overlaps with the most important feature
    group.
  - Cannot conclude that boosting in general doesn't help - only one
    configuration was tried.
  - The selected configuration (multiclass) beats the baseline by too little
    to call it a "better new model" in a practical sense; if simplicity is
    preferred, keeping the binary RF is a reasonable choice.
