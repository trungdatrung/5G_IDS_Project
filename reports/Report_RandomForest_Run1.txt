1. GOAL
--------------------------------------------------------------------------------
Binary classification of each network flow into:
    0 = Normal
    1 = Attack
This is the first run (baseline): default parameters, no tuning, to establish a
reference point for later improvements.


2. DATA
--------------------------------------------------------------------------------
Source: 2 Parquet files cleaned in notebook 01, using the UNSW-NB15 authors'
exact official train/test split.

                    Total     Normal (0)         Attack (1)
    Train set     98,934   49,825 (50.4%)    49,109 (49.6%)
    Test set      50,567   32,034 (63.3%)    18,533 (36.7%)

Cleaning steps already applied beforehand (notebook 01):
  - Dropped the `id` metadata column.
  - Dropped 8 leaky features per D'hooge et al. (PST 2022):
    ct_state_ttl, sttl, dttl, ct_dst_ltm, ct_srv_dst, ct_dst_src_ltm,
    ct_srv_src, ct_dst_sport_ltm. The paper's 9th feature, `ct_srv_ltm`,
    does not exist in this data.
  - Dropped 3 features with no discriminative power: is_sm_ips_ports,
    ct_ftp_cmd, is_ftp_login.
  - Dropped duplicate rows and contradictory rows (same features, different
    label).

Note: the train set's 50/50 ratio is not artificial balancing. It is a
consequence of removing duplicates (the Generic class is almost entirely
duplicates).

Input features: 31 columns, 28 numeric and 3 categorical (proto, service,
state). After one-hot encoding: 183 columns. `label` and `attack_cat` are not
used as features, since `attack_cat` is literally the attack type name and
would leak the label.


3. TRAINING METHOD
--------------------------------------------------------------------------------
A 2-step pipeline, fit only on the train set:
  (1) OneHotEncoder(handle_unknown='ignore') for proto, service, state.
      Values seen only in the test set (state = ACC, CLO) are encoded as
      all zeros.
  (2) RandomForestClassifier(n_estimators=100, random_state=42), all other
      parameters left at default:
        - 100 trees, each trained on a bootstrap sample of the train set
        - each node considers about 13 random columns (sqrt(183)), splitting
          by Gini
        - no depth limit
        - decision threshold 0.5

No hyperparameter tuning, no SMOTE/class_weight, no data normalization
(Random Forest doesn't need it). The test set is used only once, for
evaluation.

6. INTERPRETING THE METRICS
--------------------------------------------------------------------------------
6.1. Accuracy = 0.8176
  (TN + TP) / Total = (23,812 + 17,530) / 50,567.
  Out of every 100 flows, the model classifies about 82 correctly.
  The test set is 63.3% Normal, so a model that "always predicts Normal"
  would already reach 0.6335. The model beats that baseline by about
  18 percentage points. Since the two classes in the test set are imbalanced,
  Accuracy should not be the primary metric. Precision, Recall, and F1 matter
  more.

6.2. Precision = 0.6807 (the weakest point)
  TP / (TP + FP) = 17,530 / 25,752.
  Out of 100 times the model says "Attack," about 68 are correct and 32 are
  false alarms. In real IDS operation, this means an administrator must
  review many false alerts, which easily leads to "alert fatigue."
  Precision is low because FP is large (8,222). The cause is analyzed in
  section 7.

6.3. Recall = 0.9459 (the strongest point)
  TP / (TP + FN) = 17,530 / 18,533.
  The model detects about 95 out of 100 attacks, missing only 5.4%.
  For an intrusion detection system, missing an attack is usually more
  dangerous than a false alarm, so high Recall is a good result.
  Recall by attack type:
      Analysis, Backdoor, Worms         : 100%
      Reconnaissance 99.3% | Generic 99.3% | DoS 98.9% | Exploits 98.4%
      Shellcode                          : 95.1%
      Fuzzers                            : 81.6%   <- weakest
  Fuzzers alone accounts for 817 / 1,003 missed cases (81.5% of total FN).
  Fuzzers sends random or malformed data to a service, so its flow shape
  (byte count, packet count, timing) easily resembles normal traffic.

6.4. F1-score = 0.7917
  F1 = 2 x P x R / (P + R), a harmonic mean, so it is pulled toward the lower
  of the two metrics. Recall is very high (0.95) but Precision is low (0.68),
  pulling F1 down to about 0.79. F1 shows the model isn't yet balanced
  between "catching enough" and "catching correctly."

6.5. Specificity = 0.7433 and NPV = 0.9596
  Only 74% of normal traffic is correctly identified. About 1/4 of Normal
  flows are falsely flagged — the flip side of high Recall.
  Conversely, when the model says "Normal," it's correct 96% of the time.
  The model is very trustworthy when it concludes a flow is safe.

6.6. ROC-AUC = 0.9554
  ROC-AUC measures ranking ability: pick a random Attack flow and a random
  Normal flow, and 95.5% of the time the model scores the Attack flow as
  more suspicious. High AUC alongside low Precision shows the model
  discriminates reasonably well. The problem lies mostly in the 0.5 decision
  threshold and in the data differences between train and test (section 7),
  not in the model being completely unable to discriminate.

6.7. Train accuracy 1.00 vs. test 0.82
  The model classifies 100% of the train set correctly but only about 82% of
  the test set. This is a sign of overfitting (memorization), unsurprising
  given the trees have no depth limit. Part of this gap is also due to the
  differing data distributions between train and test (section 7).


7. ANALYZING THE CAUSE OF FALSE ALARMS (FP = 8,222)
--------------------------------------------------------------------------------
7.1. Where FP concentrates
  - By connection state:
      FIN: 7,154 FP (87% of total FP), 30.6% false-alarm rate among Normal
      FIN flows
      INT: 1,046 FP, 60.5% false-alarm rate (the highest)
      CON: only 13 FP out of 6,417 flows (0.2%)
  - By service:
      "-" (unidentified) 6,420 FP | http 1,468 FP (39.4%) | ftp 313 FP (41.6%)
      dns only 17 FP out of 2,914 flows (0.6%)
  => False alarms occur mainly on closed TCP flows (FIN) and HTTP/FTP flows.
     Almost no false alarms on DNS or open connections (CON).

7.2. FP flows that "look like attacks"
  Median comparison:
                        TN (correct Normal)   FP (Normal flagged)   TP (Attack)
      tcprtt (s)              0.0007               0.1424              0.0807
      dbytes                  1,080                  354                 354
      rate (packets/s)        798.4                  23.3                44.0
      dur (s)                 0.09                   0.85                0.59
  Normal flows that get falsely flagged look almost identical to attacks:
  slow TCP handshake, few reply bytes (same median of 354 as TP), low packet
  rate, longer duration. These are exactly the features the model considers
  most important (tcprtt, ackdat, synack, dload, rate, dbytes...).

7.3. Root cause: the Normal distribution differs between train and test
      % of Normal flows with tcprtt > 0.01 s:   train 19.0%  ->  test 41.3%
      % of Normal flows with rate < 100 pkt/s:   train 33.7%  ->  test 51.6%
      % of Normal flows with state = INT:        train  3.0%  ->  test  5.4%
  In the train set, Normal is almost always "fast," so the model learns the
  rule "slow handshake / low rate => Attack." The test set has far more
  "slow" Normal traffic, so this rule generates many false alarms.
  This is a distribution shift between UNSW-NB15's train and test sets. It
  reflects a real-world challenge: the model must run on traffic that differs
  from what it was trained on.

7.4. The model's confidence when it's wrong
  The "Attack" probability for FP cases has a median of 0.68; 25% of FP cases
  are only at 0.54-0.59. Many FP cases sit right next to the 0.5 threshold,
  i.e. the model is "hesitant."
  For reference (NOT used to pick parameters, since this is measured on the
  test set):
      threshold >= 0.5 : Precision 0.676 | Recall 0.950
      threshold >= 0.6 : Precision 0.736 | Recall 0.909
      threshold >= 0.7 : Precision 0.808 | Recall 0.863
      threshold >= 0.8 : Precision 0.879 | Recall 0.806
  Raising the threshold reduces false alarms but misses more attacks. The
  threshold must be chosen on a validation set, not on the test set.
  (The 0.5 row here differs slightly from section 4 because 286 flows have a
  probability exactly equal to 0.5 (50 trees vote Normal / 50 vote Attack);
  the predict() function assigns these flows to Normal, while the ">= 0.5"
  comparison here assigns them to Attack.)

    10. sbytes   0.0439   bytes, source -> dest
  The top 10 account for 61.1% of total importance. The model relies mainly

  source of false alarms.
  Note: importance shows which features the model uses to split the data,
  it does not prove causation.


9. CONCLUSION
--------------------------------------------------------------------------------
  + Strengths : good at detecting attacks (Recall 94.6%, ROC-AUC 0.955).
                Almost no misses on Generic, DoS, Reconnaissance, Exploits,
                Backdoor, Analysis, Worms.
  - Weaknesses: high false-alarm rate (FP 8,222, about 25.7% of Normal
                traffic), Precision only 68%. The model overfits (train
                100% vs. test 82%). Weakest on Fuzzers (Recall 81.6%).
  This result is reasonable for a baseline after removing leaky features.
  It should not be directly compared with papers using the original
  UNSW-NB15 (which keep sttl, dttl, ct_state_ttl, and duplicate data), since
  those papers typically score higher because they use the leaky features.


10. SUGGESTIONS FOR THE NEXT RUN
--------------------------------------------------------------------------------
  1. Split off about 20% of the train set as a validation set (stratified by
     label). All tuning should rely only on validation; the test set is used
     once, at the very end.
  2. Reduce overfitting: try max_depth, min_samples_leaf (e.g. 5-20),
     max_features.
  3. Re-select the decision threshold on validation to balance
     Precision/Recall per the system's requirements (prioritizing fewer
     misses or fewer false alarms).
  4. Try class_weight='balanced' or 'balanced_subsample'.
  5. Evaluate further by attack type (especially Fuzzers), and use
     permutation importance to re-check feature importance.
  6. Compare against other models (e.g. XGBoost/LightGBM, Logistic
     Regression) on the same cleaned feature set.
