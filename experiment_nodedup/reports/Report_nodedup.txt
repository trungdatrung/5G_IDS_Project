All variants drop id, downcast dtypes, and drop the 8 contaminated columns + 3

  Variant               Remove dupes   Remove conflicts   train      test
  --------------------- -------------- ------------------ ---------- ---------
  V1_nodedup            NO             yes                170,515    80,816
  V2_nodedup_nocontra   NO             NO                 175,341    82,332
  V0_official_recipe    yes            yes                 98,934    50,567

  V1 is the main variant (matches the "do not remove duplicate rows" requirement).
  V2 also keeps the conflicting rows. V0 is the control.

  CONTROL CHECK PASSED: V0 reproduces data/cleaned EXACTLY, value for value

  Scale of the deduplication step: it removes 75,775/175,341 = 43.2% of train rows
  and 31,523/82,332 = 38.3% of test rows. This is why the cleaned set shrinks so much.


================================================================================
PART 2. FINDING 1 - THE CLEANING STEP DOES NOT CREATE THE CLASS-RATIO SKEW
================================================================================
The earlier report (Bao_cao_so_sanh_3_lan_chay.txt section 3.2 cause 4, and slide 2)
claims: "The cleaning step affects the two sets DIFFERENTLY, creating a 13-point skew."

DIRECT MEASUREMENT:

                       train     test     skew
    Raw data          0.6806   0.5506   0.1300
    After cleaning    0.4964   0.3665   0.1299

    Drop in train : 0.1842 points
    Drop in test  : 0.1841 points

  => The cleaning step pulls BOTH sets down by almost EXACTLY THE SAME amount
     (0.0001-point difference). The 13-point skew was ALREADY PRESENT in the raw
     UNSW-NB15 data.

  CONCLUSION: the claim "the cleaning step itself creates a 13-point class-ratio
  skew" is WRONG and should be corrected in both the earlier report and the slide.
  The cleaning step lowers the Attack ratio of both sets, but does NOT create and
  does NOT widen the skew.

  Consequence for the Precision decomposition: the "due to class ratio" component
  (0.0540, ~23%) is still numerically correct - the class ratios of the two sets
  really are different. Only the part attributing this to the cleaning step is
  wrong; the skew is a property of the raw dataset.


================================================================================
PART 3. FINDING 2 - KEEPING DUPLICATE ROWS LEAKS TEST ROWS INTO TRAIN
================================================================================
Number of test rows that exactly duplicate (features + label) a train row:

    V0_official_recipe     1,993 /  50,567   =  3.94%
    V1_nodedup            20,960 /  80,816   = 25.94%
    V2_nodedup_nocontra   23,536 /  82,332   = 28.59%

  => Dropping the deduplication step raises the leakage rate by 6.6x. More than a
     quarter of the test set is sitting verbatim inside the train set. Every metric
     measured on that test set is inflated by rote memorization.

PART 4. TWO EVALUATION METHODS - MUST BE CLEARLY DISTINGUISHED
================================================================================
  (A) NATIVE  - measured on the non-deduplicated test set (40,408 rows).
                This is the figure a team would get if they skipped this step.
  (B) CONTROL - measured on the EXACT 25,284-row official test-final set that
                every earlier experiment used. The evaluation set stays fixed,
                so the only difference is the training data. ONLY METHOD (B)
                ANSWERS THE QUESTION.

Sizes: non-deduplicated  136,412 fit / 34,103 val / 40,408 dev / 40,408 final
       official           79,147 fit / 19,787 val / 25,283 dev / 25,284 final

IS COMPARISON (B) FAIR?
    Share of the OFFICIAL test-final rows present in the training set:
        official train-fit              3.22%
        non-deduplicated train-fit      3.67%
    Nearly identical. Reason: deduplication does not remove any feature vector, it
    only removes duplicate copies. The two train sets contain the same set of
    DISTINCT rows, differing only in how many times each repeats. So the gap seen
    in (B) is NOT caused by leakage, but by repeat counts acting as an IMPLICIT
    SAMPLE WEIGHT.

================================================================================
PART 6. ANSWERING THE QUESTION: DATA OR ALGORITHM?
================================================================================

NOT THE TRAINING ALGORITHM.
  The algorithm is kept completely unchanged on both branches. When measured on
  the same honest evaluation set, the three model stages give almost identical
  results (~0.0025 PR-AUC difference). Doubling the training data (79,147 ->
  136,412 rows) does not help either - because the added rows carry no new
  information, they are just duplicates.

  This is consistent with the earlier boosting experiment: HistGradientBoosting,
  a completely different algorithm family, also landed at the same PR-AUC level
  (+0.0003, not significant). Two independent pieces of evidence point the same
  way.

NOT THE DEDUPLICATION STEP EITHER.
  The hypothesis that "overly aggressive cleaning damaged the data" DOES NOT HOLD UP:
    - Deduplication removes no feature vector, only duplicate copies.
    - It does not create the class-ratio skew (Part 2).
    - Keeping duplicate rows makes results WORSE, not better (Part 5.1).
  The deduplication step is CORRECT and should be kept.

THE ISSUE LIES IN THE DATA'S DISTRIBUTION, NOT IN HOW IT WAS CLEANED.
  The root cause was already measured in the earlier round of experiments and is
  not overturned by this one:
    - ackdat is the most skewed feature among the 28 numeric features (KS 0.0984;
      0.2698 for Normal alone) AND AT THE SAME TIME the model's most important
      feature (permutation importance 0.0501).
    - P(Attack | slow TCP handshake) shifts from 0.80 (train) to 0.51 (test) -
      a concept shift, not a covariate shift.
    - Adversarial validation AUC 0.8012 (0.8722 for Normal alone).
    - The 13-point class-ratio skew - now known to be already present in the raw
      data.

  No cleaning approach can fix any of this, because these are properties of the
  UNSW-NB15 dataset itself.


================================================================================
PART 7. WHAT CANNOT BE CONCLUDED FROM THIS EXPERIMENT
================================================================================
  - It cannot be concluded that every other cleaning approach is useless. Only one
    change was tested here: toggling the removal of duplicate rows (and
    conflicting rows).
  - It cannot be concluded that adding data in general never helps. The data added
    here is DUPLICATE data, carrying no new information. Genuinely new data - e.g.
    labels drawn from the test distribution - remains an untried direction.
  - Variant V2 (also keeping the conflicting rows) was created and saved but has
    NOT yet been run through the model; it differs from V1 by only 4,826 train
    rows, so it is unlikely to give a different result.
